## 评估洞察

### 总体发现
- 不相关的检索上下文频繁影响 SQL 查询的相关性
- 模型经常遗漏必要的 SQL JOIN 和子句
- 即使检索上下文不理想，模型仍能生成正确的 SQL 查询
- 输出有时包含不必要的字段或缺少排序

### 歌曲特征和属性类查询
- 实际输出经常缺少与 music_main 表的必要 JOIN
- 检索上下文中经常包含不相关的信息，掩盖了相关数据
- 模型能成功识别情感值（valence）最高的歌曲
- 不相关的检索上下文节点影响了上下文相关性得分

### 按流派或主题的歌曲查询
- 实际输出经常错误引用不存在的字段或误解用户意图
- 检索上下文频繁包含不相关信息，影响相关性
- 模型输出有时缺少分组（GROUP BY）或排序（ORDER BY）等必要语法
- 尽管上下文存在问题，模型通常仍能提供与输入匹配的相关 SQL

### 歌词和内容类查询
- 模型能正确生成统计歌词中包含"love"的歌曲的 SQL
- 即使 SQL 正确，检索上下文中仍包含不相关的数据库结构
- 当表结构上下文清晰时，模型的响应通常是成功的
- 输出有时包含不必要的字段或缺少特定排序

### 歌曲和歌手统计类查询
- LLM 输出经常缺少某些预期的子句，影响精确度
- 即使上下文中存在不相关的表，LLM 仍能生成正确的 SQL
- 当上下文缺少具体查询信息时，模型无法对齐输出
- 对于指定流派的查询，当上下文中有 SQL 示例时能生成正确查询

## 多版本 A/B 对比（通用 RAG 指标）

| 指标 | V1 (基线) | V2 (P0: JOIN注入+Prompt规则) | V3 (P1: 动态FK+语义Chunk+自动纠错) | 变化趋势 |
|------|-----------|------------------------------|--------------------------------------|----------|
| Answer Relevancy | 98% | 98% | 92% | V3 下降 |
| Faithfulness | 88% | 84% | **98%** | V3 大幅提升 |
| Contextual Relevancy | 10% | 18% | **30%** | 持续上升 |
| Contextual Precision | 96% | 100% | 96% | 稳定 |

### V3 关键变更
- 动态外键提取（`information_schema` → 自动注入 JOIN 关系，零硬编码）
- 语义增强 Schema Chunk（自动提取关联关系描述）
- 自动识别主表（被引用最多的表自动补充）
- 执行反馈自动纠错（SQL 验证失败 → 错误反馈 LLM → 重试最多 2 次）

### 通用指标的局限性

V3 的 Faithfulness 从 88% 飙升到 98%，但 Answer Relevancy 却从 98% 降到 92%。分析原因：

- AR 指标用 LLM-as-Judge 判断"SQL 是否回答了用户问题"
- 同一查询有多种等价 SQL 写法（`SELECT *` vs 具体列名），LLM Judge 可能误判为"不相关"
- 通用 RAG 指标无法评估 SQL 的**执行正确性**，只能做文本层面判断

这直接推动了自定义指标的构建。

## 自定义评估指标构建

### 动机

DeepEval 内置的 4 个指标（AR、Faithfulness、CR、CP）是通用 RAG 评估指标，对 Text2SQL 有两个核心盲区：

1. **无法验证 SQL 执行正确性** — 不执行 SQL，只做文本判断
2. **无法区分语义等价的不同写法** — `SELECT *` 和 `SELECT col1, col2` 在执行结果上可能完全等价

### 学术调研

在设计指标前，调研了 Text2SQL 领域主流基准的评估策略：

| 基准/方法 | 比较策略 | 优缺点 |
|-----------|---------|--------|
| **Spider** | 列映射到 schema 属性，忽略列顺序 | 减少假阴性，但实现复杂 |
| **BIRD** | 值集合比较，忽略列名、列顺序、重复值 | 简洁有效，但可能增加假阳性 |
| **Test Suite Accuracy** (Spider 官方 2020+) | 多数据库实例交叉验证 | 减少假阳性，计算成本高 |
| **FLEX** (NAACL 2025) | 减少 EX 假阳性/假阴性的改进版 | 学术前沿，实现较新 |
| **SpotIt** (2026) | 形式化验证代替静态测试 | 最严谨，支持最广的 SQL 片段 |
| **LLM-as-Judge for SQL** | LLM 判断语义等价性 | 灵活但不确定性高 |
| **Soft F1-Score** (BIRD Mini-Dev) | 部分匹配评分 | 支持细粒度评估 |

### 指标设计

基于调研结果，设计了 3 个 Text2SQL 专用指标：

#### 1. Execution Accuracy (EX) — 核心指标

**参考**: Spider/BIRD 基准的标准评估方式

**计算方式**: 分别执行 actual SQL 和 expected SQL，比较结果集

**评分规则**:
- 1.0: 结果集语义一致
- 0.5: SQL 可执行但结果不一致
- 0.0: SQL 执行失败

**结果集比较策略**（采用 BIRD 风格，三层回退）:

```
策略 1（列数相同）: 按值排序后逐行比较，完全忽略列名/别名
  → 解决 "COUNT(*) AS song_count" vs "COUNT(*) AS cnt"

策略 2（SELECT * 场景）: 用 expected 列名在 actual 中做子集提取比较
  → 解决 "SELECT *" vs "SELECT track_name, artist_name"

策略 3（兜底 BIRD 全值集合比较）: 忽略列归属，只比较值的多重集
  → 处理所有边界情况
```

#### 2. Valid SQL Rate — 基本质量门槛

**计算方式**: 尝试对数据库执行生成的 SQL

**评分**: 1.0 = 可执行, 0.0 = 执行失败

**优势**: 不依赖 LLM Judge，直接对数据库验证，零误判

#### 3. Table Selection Accuracy — Schema Chunking 质量

**计算方式**: 从 expected SQL 提取需要的表名，与 retrieval_context 中的表名对比

**评分**: 覆盖率 = 覆盖的表数 / SQL 需要的表数

**优势**: 独立评估 Schema Chunking 环节，定位检索质量瓶颈

### 首轮自定义指标结果（V3 版本，严格比较策略）

| 指标 | Pass Rate (threshold=0.5) | 分数分布 |
|------|--------------------------|----------|
| Execution Accuracy (EX) | 100% | 1.0: 10/50 (20%), 0.5: 40/50 (80%), 0.0: 0/50 (0%) |
| Valid SQL Rate | 100% | 50/50 全部可执行 |
| Table Selection Accuracy | 100% | 50/50 全部覆盖 |

### 首轮 EX=0.5 原因分析

虽然 pass rate 100%，但真正的执行准确率 (EX=1.0) 只有 **20%**，80% 的 SQL 结果不一致。分析不一致模式：

| 模式 | 数量 | 根因 | 是否为真实错误 |
|------|------|------|--------------|
| 同行数但列/别名不同 (50=50, 7=7) | 22 | `SELECT *` vs 具体列名；别名差异 | 部分假阴性 |
| actual=1, expected=10 | 9 | LLM 解释"最高的歌曲"为 LIMIT 1 | 真实错误 |
| 行数差异大 (1 vs 50, 50 vs 20) | 9 | LLM 缺少/多了 LIMIT 或 WHERE 条件 | 真实错误 |

**关键发现**：22 个"同行数不同列"的 case 中，大部分是**假阴性** — SQL 语义等价但比较策略太严格。

### 比较策略优化

基于分析结果，将 `_results_match` 从"严格列名+值"比较改为 **BIRD 风格的三层回退策略**：

1. **列数相同** → 按值排序比较（忽略列名/别名）
2. **actual 列多**（SELECT \*）→ 用 expected 列名在 actual 做子集提取
3. **兜底** → 全值集合比较（完全忽略列归属）

**实现踩坑**：Python 3 中 `sorted()` 对含 `float` 和 `str` 的混合类型元组排序会抛 `TypeError`。所有外层 `sorted()` 需传入统一的 `key=_tuple_sort_key`（将每个值转为 `(is_none, str_repr)` 元组）。

### 优化后自定义指标结果（V3 版本，BIRD 风格比较）

| 指标 | Pass Rate (threshold=0.5) | 分数分布 |
|------|--------------------------|----------|
| Execution Accuracy (EX) | 100% | **1.0: 22/50 (44%)**, 0.5: 28/50 (56%), 0.0: 0/50 (0%) |
| Valid SQL Rate | 100% | 50/50 全部可执行 |
| Table Selection Accuracy | 100% | 50/50 全部覆盖 |

**EX=1.0 从 20% 提升到 44%**，12 个假阴性被正确识别为匹配。

### 剩余 28 个 EX=0.5 的真实问题

这些是比较策略无法弥补的真正差异，需要从 LLM 生成质量侧优化：

| 问题类型 | 典型表现 | 优化方向 |
|---------|---------|---------|
| 缺少 LIMIT | "最高的歌曲" → LIMIT 1，期望 LIMIT 10 | Prompt 规则强化 |
| SELECT * 代替具体列 | 返回全部列，期望 2-3 列 | Prompt 规则 "避免 SELECT *" |
| 缺少 ORDER BY | 结果行相同但顺序不同 | Prompt 规则 "排名类必须 ORDER BY" |

### 实现细节

自定义指标代码位于 `tests/custom_metrics.py`，通过 `--custom` 参数启用：

```bash

python tests/test_rag_eval.py --limit 50 --metrics 4

# 使用自定义 Text2SQL 指标
python tests/test_rag_eval.py --limit 50 --custom
```

所有结果自动上传至 Confident AI 平台，支持跨版本回归对比。

## V4 优化：基于自定义指标的针对性优化

### 优化目标

自定义指标明确了唯一瓶颈：**EX=1.0 只有 44%**（22/50）。而 Valid SQL Rate 和 Table Selection Accuracy 已达 100%，说明自动纠错和 Schema Chunking 无需再优化。

问题完全集中在 **LLM 生成质量**——28 个 EX=0.5 的 case 全部是"SQL 可执行但结果集不匹配"。

### 根因分析

对 28 个 EX=0.5 case 逐条分析 actual SQL vs expected SQL，归纳出三类核心问题：

| 问题模式 | 数量 | 典型表现 |
|----------|------|----------|
| LIMIT 不一致 | ~9 | 用户说"最高的歌曲"，LLM 生成 LIMIT 1，expected 是 LIMIT 10 |
| SELECT * 代替具体列 | ~10+ | `SELECT * FROM music_main` vs `SELECT track_name, artist_name` |
| 缺少 JOIN / ORDER BY | ~9 | 只查子表不 JOIN 主表；缺少排序导致顺序不一致 |

### 关键发现：向量库中毒

首轮优化（Prompt 硬约束 + 降低 temperature）后跑评估，EX=1.0 仍为 22/50（44%），**完全无变化**。

分析评估日志的 `retrieval_context` 发现：向量库（`melomane_collection`）中缓存了 **673 条之前跑评估时保存的 SQL**，其中大量包含 `SELECT *`、`LIMIT 1`、缺少 JOIN 等问题。这些有毒示例作为 few-shot 被检索出来，LLM 直接模仿，**覆盖了 System Prompt 的规则约束**。

这揭示了一个重要的架构问题：**自动保存成功 SQL 到向量库的机制是双刃剑**——如果早期生成质量差，坏 SQL 会不断自我强化，形成"有毒飞轮"。

### V4 变更清单

#### 1. Prompt 硬约束 + Negative Examples（`prompts.py`）

将原有 6 条"建议式"规则改为 7 条带 ❌/✅ 示例的硬约束：

```
1. **禁止 SELECT ***。必须明确列出需要的列名。
   ❌ SELECT * FROM "music_main" WHERE "genre" = 'pop';
   ✅ SELECT "track_name", "artist_name" FROM "music_main" WHERE "genre" = 'pop';

2. **默认 LIMIT 10**。除非用户明确指定了数量（如"一首""3个"），否则所有查询都必须加 LIMIT 10。
   ❌ 用户说"最受欢迎的歌" → LIMIT 1
   ✅ 用户说"最受欢迎的歌" → ORDER BY ... DESC LIMIT 10
   ✅ 用户说"最受欢迎的一首歌" → ORDER BY ... DESC LIMIT 1

3. 排名/最多/最少类查询必须加 ORDER BY + LIMIT，缺一不可。
4-7. GROUP BY / HAVING / JOIN ON / 不引用不存在的列名
```

#### 2. 降低 Temperature（`llm.py`）

```
temperature: 0.7 → 0.2
```

SQL 是确定性任务，高 temperature 导致 LLM 在 LIMIT 1/10、是否 JOIN 等决策上随机波动。

#### 3. 清空有毒向量库

```python
# 清空前: 673 条缓存（含大量 SELECT *、LIMIT 1 的坏 SQL）
# 清空后: 0 条
ChromaVectorStore(collection_name='melomane_collection').clear()
```

### V4 评估结果

| 指标 | V3 (50条) | V4 (40条有效*) | 变化 |
|------|-----------|---------------|------|
| **EX=1.0** | 22/50 (44%) | **26/40 (65%)** | **+21%** |
| EX=0.5 | 28/50 (56%) | 14/40 (35%) | -21% |
| EX=0.0 | 0/50 (0%) | 0/40 (0%) | - |
| Valid SQL Rate | 100% | 100% (40/40) | 持平 |
| Table Selection Accuracy | 100% | ~100% (39/40) | 持平 |

*注：50 条中有 10 条因 NeonDB SSL 连接中断（`SSL: UNEXPECTED_EOF_WHILE_READING`）导致管道层失败，非 SQL 生成问题，已排除。

| 指标 | V3 (BIRD 比较) | V4 (Prompt+Temp+清缓存) | 变化 |
|------|---------------|------------------------|------|
| EX=1.0 率 | 44% | **65%** | **+21%** |

### V4 剩余问题（14 个 EX=0.5）

初步归类，待后续逐条分析：

| 问题类型 | 预计方向 |
|----------|----------|
| 查询意图误解（COUNT vs 列举） | Few-shot 示例覆盖更多查询类型 |
| 阈值理解偏差（> 0.7 vs > 0.8） | 模糊表述的默认值规则 |
| 缺少 ORDER BY（同行数不同顺序） | 评估侧放宽排序比较 or Prompt 强化 |

### 经验总结

1. **先看数据，再定方案**：自定义指标精确定位了"EX=1.0 只有 44%"这一单一瓶颈，避免在已满分的 Valid SQL 和 Table Selection 上浪费精力
2. **向量库缓存是双刃剑**：自动保存机制在早期质量差时会形成"有毒飞轮"，需要在质量提升后清空重建
3. **Prompt 规则需要具体示例**：抽象规则（"优先使用具体列名"）不如带 ❌/✅ 的 negative examples 有效
4. **Temperature 对确定性任务影响显著**：0.7→0.2 直接减少了 LIMIT/列选择的随机波动
5. **三个改动必须同时生效**：单独改 Prompt 无效（被有毒 few-shot 覆盖），必须配合清缓存

| 问题 | 对应指标 | 根因分析 |
|------|----------|----------|
| 检索到不相关的表结构 | Contextual Relevancy (10%) | Schema Chunk 文本仅包含表名和列名，缺少语义描述和表关联信息，导致向量检索不精准 |

## 优化方案

基于 2025-2026 年 Text2SQL 领域最新研究成果，针对每个问题提出前沿解决方案。

---

### 优化 1：Schema Linking 增强（目标：Contextual Relevancy 10% → 50%+）

**问题**：当前 chunk 仅包含 `表名 + 列名`，语义信息不足，向量检索无法精准匹配用户查询意图。

**前沿方案对比**：

| 方案 | 来源 | 核心思路 | 适用性 |
|------|------|----------|--------|
| **双向 Schema Linking** | [RSL-SQL (2024)](https://arxiv.org/html/2411.00073v1) | 同时做 table→column 和 column→table 两个方向的检索，召回率达 92%，schema 复杂度降低 83% | 推荐 |
| **Query Augmentation** | [Context-Aware Bidirectional Retrieval (2026)](https://arxiv.org/html/2510.14296) | 检索前先对用户查询做增强：关键词提取、问题分解、值识别，再进行 schema 匹配 | 推荐 |
| **图结构 Schema 过滤** | [GRAST-SQL (2025)](https://arxiv.org/pdf/2512.16083) | 用函数依赖图 + Steiner 树扩展建模表关系，支持 23000+ 列规模 | 我们表少，过重 |
| **切片式 Schema 分块** | [LR-SQL (2025)](https://www.mdpi.com/2079-9292/14/17/3489) | 动态分片 + CoT 重建上下文，适合低资源场景 | 可参考 |

**推荐实施方案**：Query Augmentation + 语义增强 Chunk

```
当前 chunk: "表名: music_main, 列: track_id, artist_name, track_name..."
优化 chunk: "music_main 是音乐主表，存储歌曲基本信息（歌手、歌名、流派、发行时间等）。
           常用于查询歌手作品、按流派筛选、按年份统计等场景。
           通过 track_id 与 music_lyrics、music_audio_features、music_topic_scores 关联。
           列: track_id(主键), artist_name(歌手名), track_name(歌名)..."
```

同时在检索前对用户查询做关键词提取：
```
用户输入: "查询舞曲性最高的10首歌"
增强后:   "舞曲性 danceability 音频特征 排序 TOP10 → music_audio_features"
```

### 优化 2：表关系上下文 + 自动纠错（目标：Faithfulness 88% → 95%+）

**问题**：精简 schema 后 LLM 不知道表间如何 JOIN；偶发幻觉列名。

**前沿方案对比**：

| 方案 | 来源 | 核心思路 | 适用性 |
|------|------|----------|--------|
| **DDL 知识库** | [RAGFlow Text2SQL](https://ragflow.io/blog/implementing-text2sql-with-ragflow) | 将完整 DDL（含外键）作为知识库，LLM 查询前先获取准确的表结构和关联关系 | 推荐 |
| **执行反馈自动纠错** | [RAGFlow](https://ragflow.io/blog/implementing-text2sql-with-ragflow) + [DySQL-Bench](https://text2sql-hub.dev/approaches/rethinking-text-to-sql) | 执行 SQL → 如果报错 → 将错误信息反馈给 LLM → 自动修正 → 重试。DySQL 的研究表明这可以将幻觉率从 40% 降到 5% 以下 | 推荐 |
| **Schema 探测优先** | [DySQL-Bench (2025)](https://text2sql-hub.dev/approaches/rethinking-text-to-sql) | 生成 SQL 前先让 LLM 检查 schema 结构，理解表关系和 JOIN 条件 | 可参考 |
| **多 Agent 共识** | [SQL-of-Thought (2025)](https://arxiv.org/html/2509.00581v2) | 分解为 schema linking、子问题识别、SQL 生成、纠错四个 Agent，多轮迭代 | 过重，后期考虑 |

**推荐实施方案**：表关系注入 + 执行反馈自动纠错

表关系注入：
```
在 format_partial_schema 输出末尾追加：

表关联关系（JOIN 时使用）：
- music_main.track_id = music_lyrics.track_id
- music_main.track_id = music_audio_features.track_id
- music_main.track_id = music_topic_scores.track_id
所有 JOIN 必须通过 track_id 关联。
```

执行反馈自动纠错（新增 retry 机制）：
```
SQL 验证失败 → 将错误信息 + 原始 SQL + schema 重新发给 LLM → 生成修正 SQL → 重新验证
最多重试 2 次
```

### 优化 3：Prompt 优化 + Few-shot 增强（目标：Answer Relevancy 保持 98%+）

**问题**：LLM 生成的 SQL 有时缺少 ORDER BY、GROUP BY，或包含不必要的字段。

**前沿方案对比**：

| 方案 | 来源 | 核心思路 | 适用性 |
|------|------|----------|--------|
| **合成摘要增强 Few-shot** | [Tiger Data (2025)](https://www.tigerdata.com/blog/enhancing-text-to-sql-with-synthetic-summaries) | 为每条 SQL 示例生成语义摘要用于匹配，recall@5 从 81% 提升到 90% | 推荐 |
| **CoT 推理** | [STaR-SQL (ACL 2025)](https://aclanthology.org/2025.acl-long.1187.pdf) | 让 LLM 先推理查询意图再生成 SQL，尤其对 GROUP BY + HAVING 等复杂子句有效 | 推荐 |
| **多样性 + 相似度 Few-shot 选择** | [Prompt Design Strategies](https://arxiv.org/abs/2305.12586) | 同时考虑语法结构多样性和语义相似度来选择 few-shot 示例 | 可参考 |
| **多候选 + 自一致性** | [ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/974ff7b5bf08dbf9400b5d599a39c77f-Paper-Conference.pdf) | 生成多个 SQL 候选，通过执行结果一致性投票选最优 | 后期考虑 |

**推荐实施方案**：CoT Prompt + 规则约束

System Prompt 追加规则：
```
SQL 生成规则：
1. 涉及"最多/最少/排名/前N"时必须加 ORDER BY + LIMIT
2. 涉及"每种/各类/分组统计"时必须加 GROUP BY
3. 涉及"超过/大于N"的分组条件使用 HAVING，不用 WHERE
4. 优先使用具体列名，避免 SELECT *
5. 多表查询必须使用 JOIN ON，通过 track_id 关联
```
